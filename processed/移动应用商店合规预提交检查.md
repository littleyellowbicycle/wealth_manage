# 移动应用商店合规预提交检查

## 核心结论
> mjmirza/app-store-compliance 将 [[应用商店审核]] 规则转化为一套可执行的开源手册与预提交守卫，用于在上传前发现并阻断关键拒审风险。其覆盖 117 类拒审模式与修复、[[隐私清单]]、[[Data Safety]]、95 项监管截止日期，并可接入多种 [[AI 编程助手]]。需要注意的是，CLEAR 只代表代码扫描未发现关键风险，账户状态、协议、商店元数据、审核备注与后端可用性仍须人工核验。

## 详细内容
## 项目定位

[mjmirza/app-store-compliance](https://github.com/mjmirza/app-store-compliance) 是一套面向 iOS 与 Android 应用的[[合规自动化]]方案，由公开的 [[Apple App Store Review Guidelines]]、[[Google Play]] 政策、拒审案例和修复方法组成。它试图将拒审后的排查循环前移为提交前的[[预提交检查]]，在上传前直接指出风险、依据和修复方式。

仓库主要包括：

- **[[拒审模式库]]**：收录 117 类常见拒审模式，并关联对应政策条款与修复建议。
- **隐私与数据安全检查**：核对 [[隐私清单]]、[[Data Safety]]、运行时数据行为、SDK 声明及权限配置是否一致。
- **[[监管截止日期]]**：跟踪欧盟 AI Act、DSA、COPPA 和年龄保护法律等 95 项时间节点。
- **AI 工具集成**：将规则作为技能和提交钩子接入 Claude Code、Codex、Gemini CLI、Cursor、Copilot 等 [[AI 编程助手]]。
- **持续监控工具**：覆盖 Apple 要求、Android 政策、生成式 AI 政策、隐私、安全、无障碍和发布准备度。

## 核心工作流

### 1. 执行一次性扫描

克隆仓库后，将守卫指向包含 Xcode 或 Android 项目的目录：

```bash
git clone https://github.com/mjmirza/app-store-compliance ~/repositories/app-store-compliance
bash ~/repositories/app-store-compliance/agent-os/hooks/app-store-compliance-guard.sh "/path/to/your/app"
```

扫描不会安装软件或修改应用，主要读取项目配置和代码以发现潜在拒审风险。输出状态具有明确含义：

- `BLOCKED.`：发现关键风险，必须按照每条结果下方的修复说明处理并重新扫描。
- `CLEAR.`：未在代码中发现关键风险，但仍需完成账户和商店页面检查。
- `NOT CHECKED.`：目录中没有可识别的原生项目、临时目录不可写，或扫描未能执行；Expo 项目可先运行 `npx expo prebuild` 生成原生工程。

### 2. 建立持续提交防线

运行安装脚本可将守卫接入 AI 编程工具：

```bash
bash ~/repositories/app-store-compliance/scripts/install.sh --tool all
```

守卫会在 `fastlane`、`eas submit`、`gradle bundleRelease`、`xcrun altool` 等提交命令执行前运行。若发现关键风险，它会阻止上传并给出依据与修复方向；安装器还会验证钩子确实能够拦截提交，并保留已有配置及备份。

### 3. 补足人工审核

代码扫描无法替代完整的[[预提交检查]]，至少还应人工确认：

- 开发者账户是否有效，所有协议是否已接受。
- Google Play 账户、包名及所需注册信息是否就绪。
- 审核人员能否使用可用的演示账户访问真实后端。
- 隐私表单、Data Safety、控制台声明和应用实际行为是否完全一致。
- 内购、权限、账户删除、审核备注和商店元数据是否合规。
- 目标地区是否存在尚未到期的监管义务。

## 检查重点

仓库将最常导致拒审的两个问题置于优先位置：

1. **演示账户可用**：审核账户真实存在，后端服务稳定，且审核说明足以让审核人员进入应用。
2. **隐私声明一致**：应用、第三方 SDK、数据收集用途、追踪行为、权限和平台申报必须相互对应。

除上述高频问题外，规则库还会覆盖[[内购规则]]、权限最小化、账户删除、误导性元数据、儿童保护以及外部 AI 服务披露等模式。扫描结果通常按严重程度排序，并尽量提供触发文件、行号、政策依据和具体修复建议。

## [[持续合规监控]]

仓库提供多组独立监控脚本：

- `monitor.py`：跟踪 Apple 开发者要求，覆盖 25 个关键领域。
- `monitor-regulatory.py`：整理欧盟、英国、美国、加拿大、澳大利亚和新加坡的监管事项。
- `monitor-android.py`：检查 Android 与 Google Play 要求。
- `monitor-ai-policy.py`：检查 Apple 和 Google 的生成式 AI 政策。
- `monitor-privacy.py`、`monitor-security.py`：检查移动端隐私与安全要求。
- `accessibility-audit.py`：执行静态无障碍扫描。
- `release-audit.py`：结合应用与商店元数据生成发布准备度报告。

多数监控器默认使用内置示例公告，只有显式启用实时数据时才应把结果视为最新信息；输出中的 `Data.` 行可用于判断来源状态。监控结果还可接入 [[CI/CD]]，将规则变化转化为迁移任务或待办事项。

## 来源可信度机制

项目使用 `verify-citations.py` 校验文档中的外部链接。其重点不只是确认页面返回成功，而是通过伪造链接对照样本检测内容指纹，以区分真实来源、站点故障、反爬拦截和疑似虚构引用。这一机制适合迁移到其他规则型知识库，降低“链接存在但内容未经证实”的风险。

## 使用边界

- 该项目是工程化检查清单与风险提示工具，不能保证审核通过，也不能替代平台规则或法律意见。
- 代码扫描无法读取开发者后台状态、协议、审核备注和部分真实运行行为；无法验证的项目会被主动提示，而不是默认视为安全。
- 无障碍检查属于静态分析，对图标对比度、自定义控件焦点顺序及运行时可见性判断有限。
- README 中关于审核量、拒审率和 AI 编程增长的数据具有时效性，引用前应回查 Apple、Google 或原始统计来源。

## 推荐执行顺序

1. 对目标项目运行一次守卫扫描。
2. 按严重程度修复关键和高风险问题，然后重新扫描至 CLEAR。
3. 对照人工清单核验账户、审核准备度、隐私申报、内购、权限和商店页面。
4. 根据发行地区检查未来 90 天的 [[监管截止日期]]。
5. 在 AI 工具或 CI 流程中安装提交钩子，并定期更新仓库、验证引用来源。
